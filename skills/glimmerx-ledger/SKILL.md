# GlimmerX 账本

本地、单用户、双式记账。你通过 `127.0.0.1` 上的 MCP 服务读写用户自己的账本。
**金额与汇总全部由后端计算**，你只负责传参、核对、转述结果。

**只有新增能力**：这套工具里没有改、删、撤销。写错了只能由用户在 GlimmerX 里撤销，
所以写前核对账户与分类，比事后补救便宜得多。

## 连接

- 地址：`http://127.0.0.1:17823/mcp`（端口以 GlimmerX 设置页「自动化（MCP）」为准）
- 鉴权：`Authorization: Bearer <token>`，静态令牌，无 OAuth
- 传输：Streamable HTTP，协议版本由客户端协商（支持 `2024-11-05` 至 `2026-07-28`）
- 连不上通常不是配置错：服务只在账本解锁且「本地 MCP 服务」已开启后才启动。
  让用户解锁并开启后再试。已启动后再锁账本的话端口仍在，但每个工具都会返回锁定错误。

## 约定

- **金额一律整数分**：`1850` = ¥18.50。不传小数、不传字符串、不做四舍五入。
  单笔上限 100,000,000.00 元。
- **分只是传参单位，不是展示单位**：对用户说话、草稿、回执、图表、汇总里所有金额一律写成元（`¥38.00`），
  不写「3800 分」「= 3800 分」这类换算尾巴。用户明确要求过不要看到分。
- **口语金额自己换算**：`11.1 元` → `1110`、`4.2 元` → `420`、`20元` → `2000`。
  小数先补到两位再乘 100——`11.1` 是 ¥11.10 不是 ¥11.01，更不是 110 分；心算后再用整数分回读一遍确认位数。
- **日期 `YYYY-MM-DD`**；省略即今天（本机时区）。
- **账户分四类**：`asset` / `liability` 是真正的钱包（可转账、计入净资产）；
  `expense` / `income` 是分类的镜像账户，只承载损益，不能当钱包。`list_accounts`
  和 `get_balances` 会把四类一起返回，算净资产或总余额时只取前两类。
- **账户名在四类之间统一解析**：先不区分大小写精确匹配，再唯一子串匹配（结果带
  warning），多处命中直接报错。名称一律取自 `list_accounts.name`，别拿分类名当账户名。
- **分类只属于损益**，转账没有分类。分类名按「精确（区分大小写）→ 包含 → 新建」
  解析，**包含匹配可能落到别的分类上**，所以只用 `list_categories.name` 的精确名称。
- 余额同样是整数分，负债为负值。
- 一次调用只记一笔交易，一笔交易只承载一个分类。

## 先读后写

写之前必须确认名称，不要凭记忆编：

1. `ledger_status` — 是否解锁、当前信任模式
2. `list_accounts` — 你即将使用的账户名与类型
3. `list_categories` — 分类名

账本锁定时 `ledger_status` 本身返回错误（不是 `unlocked: false`）：
**停下来让用户在 GlimmerX 里解锁**，重试无意义。

## 工具

| 工具 | 用途 |
| --- | --- |
| `ledger_status` | 解锁状态、信任模式、数据库路径 |
| `list_accounts` | 全部账户：id、名称、类型、余额 |
| `list_categories` | 全部分类：id、名称、类型 |
| `query_transactions` | 按日期/账户/分类/关键字查交易（单页） |
| `get_balances` | 只要余额，比 `list_accounts` 便宜 |
| `summary` | 区间收支合计：收入、支出、净额 |
| `record_transaction` | 记一笔支出 / 收入 / 转账 |
| `create_account` | 建账户（**默认被拒**） |

返回是 JSON，但**字段名不统一**：视图类是 camelCase（`transactionId`、
`balanceCents`、`incomeCents`），`query_transactions` 的列表项是 snake_case
（`display_amount`、`flow_amount`、`postings_summary`）。按实际返回的字段名读，
不要按习惯拼。写工具结果里 `warnings` 非空表示后端替你猜过（近似匹配、新建分类），
必须转告用户。

`query_transactions` 参数：`from`、`to`（含端点）、`account_id`、`category_id`、
`keyword`（描述子串）、`limit`（1–100，默认 50）。只返回首页，没有翻页游标。
**返回条数等于 `limit` 就当被截断**——一个月也可能超过 100 笔，聚合值与 `summary` 对不上时先看
条数，再按周或按分类切开重拉，不要拿首页当全量。
列表项的 `display_amount` 恒为正（借方总额），`flow_amount` 才是资金流向
（付款为负、收款为正、转账为 0）——复述金额时用 `flow_amount`。

`category_id` 只认 `list_categories` 的 id。`list_accounts` 里有同名镜像账户（`工资`、`餐饮` 都各有一个），
把那个账户 id 传进来**不报错、返回空数组**——看到 `[]` 先怀疑 id 取错了分类表，别下「没有记录」的结论。

资源比等价的工具调用更省，只需快照时优先用：

- `glimmerx://accounts`
- `glimmerx://categories`
- `glimmerx://report/{YYYY-MM}`（模板，替换成 `2026-11`）

## 收支汇总

「本月/本周收支怎么样」「帮我做个汇总」按这四步走，顺序不要换：

1. `summary(from, to)` 取三个总数（或读 `glimmerx://report/YYYY-MM`，一次拿到整月三个数）。
   这是权威口径，直接引用，不要自己加总后当成结论。
2. `query_transactions(from, to, limit=100)` 拉明细，用于分类拆分。**单页无游标**，
   区间内超过 100 笔就只有前 100 笔。
3. 在代码里按 `category_names[0]` 聚合：支出取 `-flow_amount`，收入取 `flow_amount`；
   `category_names` 为空的行跳过（见下）。**然后对账**：分类合计必须等于第 1 步的
   `expenseCents` / `incomeCents`，差值为 0 才能汇报。差值不为 0 就是明细被截断，
   把区间按周或按天切开重拉，别把残缺的分类表发给用户。
4. 记账方向永远看 `flow_amount`，不要用 `display_amount`：后者恒为正，
   `flow_amount == 0` 且 `category_names` 为空的行是资产/负债之间的转账
   （如「我的资产 → 活期」「→ 小孩基金」），**不计入收支**，单独列一行说明即可。

输出格式：先「收入 / 支出 / 净结余」三项表，再按金额降序的支出分类表（金额 + 占比），
收入项逐条列出（工资类通常就一笔）。区间没走完时标题写「截至 MM-DD」，别叫「本月合计」。

### 每日收支图

「给一个本月每天的收支图」这类可视化，跑 `scripts/daily_bars.py`，别手搓画图代码：

1. `summary(from, to)` 拿权威三数，再 `query_transactions(from, to, limit=100)` 拉明细，
   按 `date` 聚合成 `{天: [支出分, 收入分]}`（支出取 `-flow_amount`，收入取 `flow_amount`，
   `flow_amount == 0` 的转账跳过）。
2. 把这两个数和每天的数组写进 JSON，`expect` 填 `summary` 的 `expenseCents` / `incomeCents`——
   脚本会断言，对不上就是明细被截断或聚合写错，先修数据再出图。
3. `python scripts/daily_bars.py data.json` 出 PNG，路径在 `$TMPDIR`；出图后自己看一眼
   （中文是否乱码、标签是否压住柱子、大额日是否把其余柱子压平），再用 `MEDIA:<path>` 发出。

版式固定双面板：上面全量（单笔最大支出日会压平其他柱，所以必须有全景），下面剔除那一天看日常。
页脚放本月合计三数和最大支出日的构成说明。中文字体用 `C:/Windows/Fonts/msyh.ttc`
（粗体 `msyhbd.ttc`），绘图用 Pillow 直接画——本机环境自带 Pillow，不要为此装绘图库。

手改 Pillow 代码时两个必修点：`ImageDraw.rectangle` 要求 `y1 >= y0`，极小值算出的柱顶会落到基线以下
而直接抛 ValueError——先把柱高夹到 ≥3px；数值标注只放在够宽的柱子上，8 列以上改用轴下小表，
否则小额的标签会互相压盖。

### 年度 / 多月看板

「画个 dashboard 看今年趋势」跑 `scripts/year_dashboard.py data.json`，四块固定版式：
KPI 卡（收入 / 支出 / 净结余 / 高支出月）、月度收支柱、累计净结余折线、支出 TOP10 + 收入构成。

1. **每月一个 `summary(from, to)`，放进同一个 tool_call 的 `calls` 数组并行发**，别一个回合一条。
2. 累计净结余自己逐月累加，末值必须等于区间 `summary.netCents`；月合计写进 JSON 的 `expect`，
   脚本会断言——对不上就是漏月或某月被截断。
3. 分类拆分优先用 `get_balances`：`expense` 类账户余额之和 = 区间总支出，`income` 类之和 = 总收入。
   判等成立就不必再拉几百笔明细。**前提是该区间覆盖账本全部历史**；账本里已有更早年份时
   这些余额是跨年的，必须回到 `query_transactions` 分月拉并逐月对账。
4. 版式两个坑：柱顶标数值在 8 列以上必然互相压盖——**数值改成轴下小表**；右侧金额用固定列
   `anchor="rm"` 停在面板内边距里，否则长金额溢出面板、盖到隔壁图表。
5. 「平账专用」这类调账分类不是消费：灰色 + † 标记 + 脚注，占比异常高时口头点出来（如 8 月占一半），
   不要让它跟真实消费一起排在 TOP 榜里不吭声。
6. 出图后自己看一遍再发（中文、标签压盖、大额月是否把其余柱子压平），然后 `MEDIA:<path>`。

数据存疑时提问而不改数：某个分类是负债还款（助学贷款、房贷、车贷）且占比异常高，
可能是把还本记成了支出、与负债账户重复计算——指出这一点并问是否要拆开，
不要自行调账（本套工具也改不了）。

## 按人 / 按主题查（「给母亲和家里花了多少」「今年工资几次、共多少」）

账本没有「人」这个维度，只能**分类 + 描述关键词**两路捞，再自己去重：

1. 整类拉：`query_transactions(category_id=<list_categories 的 id>, from, to, limit=100)`。
   工资、年终奖、人情往来、老婆转账都是现成分类，整类拉一笔不漏。
   只要金额、不要明细时走快路：`get_balances` 里同类账户的余额就是该类累计
   （`expense` 为正、`income` 为负），一次调用顶掉整类拉取；前提是该余额覆盖你要的区间
   （账本至今只有 2026 年流水时才成立）。两种途径的数字必须一致，不一致就回明细逐笔核。
2. 关键词拉：描述是自由文本，**别名各查一遍**——`母亲` ≠ `老妈` ≠ `妈`，`媳妇` ≠ `老婆`。
   一次一个词，别指望一次命中所有写法。
3. 合并去重：同一笔可能既命中关键词又在整类里，按 `id` 去重，不要相加两遍。
4. 排除转存：`flow_amount == 0` 且 `category_names` 为空的是账户间转账（→ 小孩基金、→ 活期），
   不是花销，不要算进「给家人花了多少」。
5. 占比的分母用 `summary` 的区间总支出，不要用自己零件加出来的数。
6. 收入类（工资）笔数少，拉完做交叉验证：`工资` 账户 `balanceCents` 的绝对值应等于全年工资合计
   （收入账户余额记负），对得上再报；年终奖是单独分类，报「薪资」时另外说明、别悄悄并进去。

「家人」「家里」这类词有歧义：**先给主数，再用口径表请他挑**，不要只回一句反问，也不要含糊地报一个总数。

| 口径 | 边界 |
| --- | --- |
| 本人（母亲等） | 转账 + 代付（机票、看病、衣物） |
| ＋探亲路费 | 回家机票、回家路上支出——本人出行，默认不算 |
| ＋亲戚人情 | 小叔/村里人红白事——非直系，默认不算 |
| 配偶 / 子女 | 「老婆转账」整类 + 红包 + 代还贷款；孩子常常只有转存、没有消费 |

还本性质分类（助学贷款）出现在家人合计里时，补一句「若属归还本金，实际是负债减少」，给出剔除后的数。

## 预算问题

预算额度不在 MCP 接口里：`list_resources` 只给 `accounts` / `categories` / `report/{YYYY-MM}`，
没有预算或额度资源，`list_*` 与 `summary` 也都不含它。被问「我的预算还剩多少」时：

1. 一句话说明读不到预算设定，只有实际收支；
2. 给出区间内的真实支出（`summary` 的口径，别自己加总）；
3. 请用户报额度（「本月预算 1.5 万」），再据此算剩余和已用比例。

不要凭历史支出猜一个额度，也不要拿「平账专用」「其他」这类分类的余额冒充预算。

## 记一笔

### 标准流程（顺序固定）

1. `list_accounts` / `list_categories` 取准确名称（同会话内已取过可复用；账户被改过就重取）。
2. **不查重**：用户明确说过「输入记账的肯定没记过」，所以新记账请求不做预查重，直接进下一步。
   防重复靠幂等键（见下），不靠预先翻库。三种例外仍要查：用户说「可能记过了 / 帮我查一下」；
   补记很久以前的历史；同一天同一描述紧接着又来第二条。
3. 拆清四要素：金额（分）、日期（`昨天`/`前天` 自己换算成具体日期）、账户、分类。
   **先用历史口径定分类与账户**：拿不准口径时做一次**轻量参照查询**
   `query_transactions(keyword=<名词>, from=<近 90 天>, limit=5)`，只为读 `postings_summary` 看这笔描述
   惯用的钱包账户与分类——它不是查重门槛，也别让它变成「先查再问」的额外回合。命中就照旧口径写进草稿
   （「母亲转账」→ `人情往来` / `我的资产` / 沿用旧描述），不再问分类；同会话里已见过的记录直接复用，不重复查。
   历史里没有同类项、或命中多种互相矛盾的写法时，才**不自动新建、也不挑个近似的顶替**：
   用 `clarify` 把 2–4 个现有候选（如 `日常` / `服饰` / `其他`）列给用户选，拿到答复再往下走。
   同日已有同描述记录时，草稿后补一句「今天已有一笔 ¥X.XX，这是第二笔」再照记——提示不等于拦截。
4. 报草稿求确认：金额、日期、分类、账户、描述五项一次给齐，用户点头才写。
5. `get_balances`（写**前**，供回执「记账前」列）→ `record_transaction`（带幂等键）→
   响应里拿到 `transactionId` 才算成功。
6. 写后立刻 `get_balances` + 本月 `summary`，与回执逐格对照后再发。差额对不上先看是不是
   账本在你两次调用之间被 App 写过（见回执规则最后两条）。

### 少问、短草稿、一次确认（用户偏好）

用户明确要求「少一点交互确认」，但**确认这一步不因偏好豁免**（见红线）。能省的是问句，不是把关：

- **能从历史推断就别问**：一次轻量参照查询（或同会话里已有的记录）就够看出这笔描述惯用的钱包账户与分类
  （「晚饭」→ `我的资产` / `餐饮`，「滴滴打车」→ `我的资产` / `交通`）。直接写进草稿让他否决，
  而不是先问「记哪个账户」。
- **草稿压到最短**：一张五项表，或一行
  `¥38.00 · 2026-11-13 · 餐饮 · 我的资产 · 晚饭 —— 确认就记`（只写元，不写分）。不复述用户原话，
  不解释流程，不加「如需修改请告知」这类客套。
- **确认只做一次**：草稿 → 用户点头 → 落库 → 回执。不要中间再插入一次「这样可以吗」，
  也不要落库后再问「还要记别的吗」。
- **被要求直接落库时**：一句话说明本套工具没有改/删、错账只能他在 GlimmerX 里撤销，因此每笔仍需
  一次确认；然后照常给短草稿。不用长篇辩解，也不要因此变冷淡。

```json
{
  "kind": "expense",
  "amount_cents": 1850,
  "date": "2026-11-14",
  "description": "午饭",
  "source_account": "微信",
  "destination_account": null,
  "category": "餐饮",
  "idempotency_key": "lunch-2026-11-14"
}
```

| `kind` | 必填 | 说明 |
| --- | --- | --- |
| `expense` | `source_account` | 钱从 `source_account` 出，方向用 `category` 定 |
| `income` | `destination_account` | 钱进 `destination_account`，来源用 `category` 定 |
| `transfer` | 两个账户 | 两边都要资产/负债、不能同一账户；不带 `category` |

`source_account` / `destination_account` 必须是资产或负债账户，损益那一侧用 `category`
指定（分类不存在会新建）：

- `expense`：`source_account` 必填，`category` 或损益类 `destination_account` 给一个。
- `income`：`destination_account` 必填，来源侧要靠 `category`（或 `source_account`）。
- `transfer`：两个都要，且不能再给 `category`（「转账不使用分类」）。

**MCP 表达不了拆分**：一笔交易只能有一个分类和一个对手账户。遇到"一次购物多个分类"
这类真实事件，请让用户在应用里手工记，不要拆成两笔编出来。

### 幂等键：可能重试就必须传

账本是真实账目，重复记一笔要用户手工去查、去删。

- 一次逻辑写入配一个键；真正的新写入换新键。重试（超时、传输失败、重启）
  **沿用同一个键**，首次成功的结果原样返回，不会多写。
- 不传键就没有任何保护，两次调用就是两笔。
- 返回 "still being processed" 表示上一次调用还没结束：等一会儿用**同一个键**
  重试，不要为了"让它过"而丢掉键。
- 只有响应里带 `transactionId` 才算记账成功。

### 信任模式

| 模式 | `record_transaction` |
| --- | --- |
| `readonly`（默认） | 拒绝，让用户在设置里改成「信任」 |
| `trust` | 直接写入 |

服务端没有二次确认。信任模式下用户的兜底是应用里的撤销按钮，所以**不要批量连写**：
一笔一记，逐笔告诉用户记了什么，否则用户分不清该撤销哪条。

### `create_account` 是独立开关

默认关闭，关闭时调用被拒。**不要**用"记到某个猜的账户"绕过：要么请用户先建账户，
要么请用户打开「允许 AI 自动建账户」。

参数：`path`（必填）、`description`、`opening_balance_cents`、
`opening_balance_date`、`idempotency_key`。

- `path` 首段决定类型，合法首段为 `Assets` / `Liabilities` / `Expenses` /
  `Incomes` / `Equity`（单复数均可），其余段拼成账户名：`Assets/招商银行`。
- 给 `opening_balance_cents` 会额外生成一条对 Equity 的期初分录。
  用户没明确提到期初余额时不要传。
- 名字在同类型下重复会被拒（「账户名称已存在」）。

## 记账成功回执格式

用户要的是「好看、能一眼核对」的回执，不要一行流水账。成功（拿到 `transactionId`）后按固定版式回：

```markdown
💰 **记账成功** · 🔴 支出

## −¥4.20

| 明细 | 内容 |
| --- | --- |
| 📅 日期 | 2026-11-14 |
| 🍔 分类 | 餐饮 |
| 🏦 账户 | 我的资产 |
| 📝 描述 | 买豆腐 |
| 🔖 单号 | `fc97be65-01a0-454b-a2df-6d169e3cf7e4` |

💵 **余额变化**

| 账户 | 记账前 | 记账后 |
| --- | --- | --- |
| 🏦 我的资产 | ¥8,620.75 | **¥8,616.55** 🔻 |
| 🍔 餐饮累计 | — | **¥13,517.53** |

📊 **本月** 支出 **¥11,549.05** ｜ 收入 ¥25,052.95 ｜ 结余 **¥13,503.90**
```

**方向色标**（Feishu 不支持文字着色，不要写 HTML / <font>，只用 emoji 表达颜色）：
🔴 支出 / 🟢 收入 / 🔵 转账；余额上升加 🔺、下降加 🔻。

规则：

- 首行 `💰 **记账成功** · <色标> <方向>`；金额另起一行用 `##` 放大，符号按方向给（支出 −、收入 +、转账不带号）。
- 明细表顺序固定：日期 → 分类（转账换成对方账户）→ 账户 → 描述 → 单号；单号用行内代码，不截断。
- 余额表固定三列「账户 / 记账前 / 记账后」；前值取自写前 `get_balances`，写后立刻再取一次核对，拿不到前值就留 `—`，绝不编。
- 转账不出「分类累计」行；支出不出「收入累计」行。
- `warnings` 非空时表下加一行 `⚠️ **后端提示**：<原文>`。
- 末行的「本月」三个数取自 `summary` 的真实区间结果，不要自己估；跨月就写实际区间。
- 上一轮写入成功但回执没发出去（被打断、掉线、超时）时，下一轮第一段先补发那条回执并标明
  「上一笔」，再处理新请求；不要因为用户已经问了下一笔就把它吞掉。
- 账本是并发写入的：用户会同时在 App 里记。**不复用上一条回执里的「记账后」「本月」数字**，
  每次都重取；若月度支出比上一张回执多出的金额大于本笔，「差额来自别处」——用
  `query_transactions(from=月初, to=今天)` 按 `created_at` 找在你两次调用之间落库的条目
  （`created_at` 是录入时间，可能远晚于 `date`，所以别只按日期筛），一句话说明金额、分类、时间，
  不要沉默，也不要把它算进本笔。

## 红线

- 不编造账户名或分类名：先 `list_*`，再从中取。
- **未经用户对这一笔的明确确认，不落库**——包括用户说「以后把握大就直接记」的情况。确认是红线，
  不是可以优化掉的交互步骤：没有改/删能力，错账的代价全落在用户身上。
- 不把一个真实事件拆成多笔 `record_transaction`；拆分场景交回用户。
- 不确定是否写过（用户自己提出，或同一描述连记两次），先 `query_transactions` 查，再用同一个键重试。
- 分类缺失不构成把转账记成支出的理由。
- 响应里没有 `transactionId` 就不要说记好了。

## 错误处理

错误以工具结果返回（带 `isError`），读文本按下面处理：

| 返回文本 | 含义 | 处置 |
| --- | --- | --- |
| `数据库未解锁` / `Database is locked` | 账本已锁 | 告知用户去 GlimmerX 解锁；不重试 |
| `read-only` / `Not authorized` | 只读档或建账户开关关闭 | 告知用户去设置调整；不重试 |
| `still being processed` | 同一个键正在处理 | 稍后同键重试 |
| `找不到该名称的账户`、`账户不存在` | 名称写错 | `list_*` 后用准确名称重试 |
| `匹配到多个账户` | 名称不唯一 | 用 `list_accounts` 里的完整名称重试 |
| `该账户已停用` | 账户被停用，不能记账 | 让用户启用或换账户 |
| `不允许转账的账户类型` | 转账端点不是资产/负债 | 换钱包账户；本意是收支就改用 expense/income |
| `账户名称已存在` | `create_account` 路径撞名 | 换路径，或让用户处理 |
| `分类名称不能为空` | `category` 传了空白 | 修参数后重试 |
| `金额必须为正数`、`金额格式无效` | 分值为负或超上限 | 修参数后重试 |
| 日期格式无效 | 不是 `YYYY-MM-DD` | 修参数后重试 |
