## 1. 对标口径

| 分组 | 产品 | 取它对标什么 |
| --- | --- | --- |
| 严格复式 / 桌面 | GnuCash、Beancount + Fava | 分录级对账、计划交易、报表扩展、导入格式 |
| 自托管全功能 | Firefly III | 规则引擎、标签/附件、周期账单、REST API |
| 本地优先预算 | Actual Budget | 本地优先、信封预算、导入迁移、自定义报表 |
| 用户期待基线 | Monarch、YNAB、Copilot、Quicken Simplifi | 账单识别、预测、AI 问账与周报、保存视图 |
| 国内录入体验 | 钱迹、随手记、鲨鱼记账 | 三步记账、周期/分期、小票与语音、账单导入 |

前两组是 `01-overview.md` 明确声明的借鉴对象；后两组用来界定
「普通用户默认会期待什么」，不作为功能对齐的硬指标。

## 2. 当前实现基线

盘点时的快照：8 个页面、74 个 IPC 命令、`SCHEMA_VERSION = 3`、
11 张表 + 1 视图、6 张报表（另有设置页的数据体检）、
MCP 8 个工具 + 3 个只读资源。后端 474 个测试通过、行覆盖门禁 94%；
前端覆盖率门禁约 7%，无 E2E。

一句话判断：**账本内核（正确性、安全、可审计性）比同类扎实，
差距集中在「录入自动化」「数据闭环」「向前看」三处。**

## 4. 领先项与主动取舍

### 4.1 领先，不要为了「对齐」而削弱

- 分录为唯一真相 + 分类与损益账户 1:1 + 余额不落库，报表和列表共用口径。
- 分录级对账（`postings.cleared` / `reconcile_id`），一笔转账只有一侧上账单
  也能处理；多数消费级产品是交易级标记。
- SQLCipher 全库加密 + 锁定即丢弃密钥，没有云端副本。
- MCP 两档信任 + 幂等键 + 建账户二级开关，是同类里少见的可被外部
  agent 安全操作的账本接口。

### 4.2 主动取舍，不算缺陷

单币种（CNY）、无云同步 / 移动端 / 多用户、不接银行与第三方 API、
CSV / Beancount 导入导出已下线、硬删除无回收站、不做操作审计日志。
其中「导入导出下线」确实让数据可迁移性偏弱，但按既定方向，
补法应是**备份恢复**，不是把导出加回来。

## 6. 建议新增的功能

<!-- markdownlint-disable MD013 -->

| # | 优先级 | 功能 | 理由 | 前置 / 成本 |
| --- | --- | --- | --- | --- |
| N1 | P0 | 周期 / 模板交易 | 房租、工资、订阅是最高频的重复录入；四家同类都有，`01-overview.md` 列在「未做」而非「不做」 | 建议「到期提醒 + 一键确认生成」，不要后台静默落账，契合本地克制的定位；会动 schema |
| N2 | P0 | 规则自动分类 | 描述包含 X → 分类 / 账户，可回溯应用到历史交易；同一套规则能服务手工录入、AI 提案与 MCP 写入，投入产出比最高 | 会动 schema；建议先做只读回放预览再落库 |
| N3 | P1 | 收款人 + 交易模板 | 重复录入提速，也是规则引擎最自然的匹配字段 | 会动 schema |
| N4 | P1 | 批量操作 | 多选改分类 / 改账户 / 删除，配合现有虚拟列表 | 纯前端 + 复用既有命令 |
| N5 | P1 | 标签 / 票据附件 | 跨分类横向维度（装修、旅行）；票据是复式账本最自然的凭证 | 会动 schema；附件需先定存储位置（加密库内 blob 还是外部目录）与备份范围 |
| N6 | P2 | 未来现金流 / 账单日历 | 基于周期交易推 30 / 90 天，是「向前看」最低成本的一步 | 依赖 N1 |
| N7 | P2 | AI 只读问账 | 「本月餐饮比去年多多少」；复用现有 MCP 只读工具，只读不写库，不破坏信任模型 | 依赖现有 `ai.*` 配置；注意只发必要数据给模型 |
| N8 | P2 | 保存的报表视图 | URL 状态已齐（`useReportQuery`），加一层命名保存即可对标 saved views | 纯前端 |
| N9 | P3 | 小票 / 语音识别 | Monarch、随手记已普及 | 与「数据不出本机」冲突（需外部模型），优先级最低 |

## 7. 明确不建议

以下事项已被 `MEMORY.md` / `BACKLOG.md` / `docs/design/09-double-entry.md`
决策过，除非前提变化，不要再提出：

- 多币种与汇率换算；
- 软删除、回收站、撤销栈（AI 回执的撤销是删除交易，不是软删除）；
- 全局快捷键、失焦锁定；
- CSV / Beancount / CSV 导入导出；
- 云同步、移动端、多用户协作、银行直连；
- MCP `confirm` 信任档（服务端「先落库 + 应用内撤销」是刻意取舍，
  事前确认由 Agent 侧承担）；
- 四个旧报表加回、报表页把时间粒度改回筛选控件；
- 读写连接池、报表聚合改 `i128`、IPC 契约自动生成。

## 8. 落地前置约束

- **改数据库必须先经用户确认**（`AGENTS.md` 硬规则）。
  `schema_v1.sql` 已冻结，v3 尚未发版；N1 / N2 / N3 / N5 / I4 大概率
  需要 `schema_v4.sql` 与 `migrations.rs` 注册。
- 金额解析、加减、汇总只在 Rust 后端，库里存整数分；前端只格式化。
- 用户可见文案只在后端产出，键需同时写进 `src/i18n/locales/{zh,en}.json`
  的 `errors` 段并跑 `tools/gen_error_messages.py`。
- 日期用本地时区的 `YYYY-MM-DD`，禁 `Utc::now()` 与
  `toISOString().split("T")[0]`。
- 新增 `commands/*.rs` 会拉低 94% 覆盖率门禁，需按约定补 `mod ipc_tests`。

## 9. 建议的落地顺序

1. **先闭环、零 schema**：I1（备份恢复）+ I2（自动更新）+ I3（文案清理）
   与 N4（批量操作）、N8（保存视图）。这几项不动数据库，风险最低。
2. **再定一次产品边界**：周期交易、规则、收款人、标签、附件是否要做，
   以及预算历史快照的口径。确认后统一开 `schema_v4`，避免反复迁移。
3. **最后做向前看**：N6 依赖 N1，N7 复用 MCP 只读工具，放在自动化稳定之后。

本文只做盘点与建议，未改动任何产品代码。条目被采纳后应移入
`BACKLOG.md` 的「未决」表，并从本文删除。
